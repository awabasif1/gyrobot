Part 0The one idea behind the architecture

Almost every structural decision in this repository follows from a single observation: perception is slow and unpredictable, and balancing cannot tolerate unpredictability at all.

A camera frame takes 20 ms to arrive on a good day and 200 ms on a bad one, because it crosses a WiFi link shared with every other laptop in the room. GPU inference takes 8 ms most frames and 25 ms when the driver decides to do something else. None of that is fixable; it is what networked perception costs.

Meanwhile, an inverted pendulum with its centre of mass 12 cm above the axle falls over on a timescale of roughly sqrt(L/g) ≈ 110 ms. A control loop that occasionally pauses for 200 ms to wait for a JPEG does not balance a robot. It drops it.

So the two jobs are put on different processors, and the slow one is never allowed to block the fast one:

ProcessorRateJob, and what happens when it stalls
Arduino Mega 200 Hz, fixed Read the IMU, run the PID, drive the motors. Never waits for anything. If no command has arrived for 400 ms it zeroes the steering and keeps standing up.
Laptop + GPU 15–30 Hz, variable Find the target, decide where to go. If it crashes, the robot stops steering and stands still.
ESP32-CAM best effort A camera with an antenna and a serial port. Knows nothing about balancing. If it dies, same as above.
The invariant to protect

The balance loop reads whatever command arrived most recently and runs regardless. It never blocks, never retries, never waits. Any change that introduces a wait into loop() in balance_controller.ino — a delay(), a blocking serial read, a library call with internal retries, a Serial.print of a float in the control path — breaks the one property that makes this system work.

This also explains a structural choice that looks like extra work: the degradation path is layered three deep, and each layer works when the others are gone.

LayerWhereWhat it covers
1. Target lostLaptop, CommandShaperHold the last command 350 ms, then ramp to zero over 400 ms. Covers a missed detection or one corrupt frame.
2. Command timeoutMega, CMD_TIMEOUT_MSNo valid line for 400 ms → steering forced to zero. Covers the laptop crashing, WiFi dropping, the UART cable falling out.
3. Clean shutdownLaptop, Ctrl-C handlerSends L:0.00,T:0.00 before exiting. Without it, quitting the program leaves the Mega turning forever.

Layer 2 does not depend on layer 1, and layer 3 depends on neither. The Mega's timeout is the authoritative one, because the Mega is the only board that still functions when the other two are gone.

1.3  Seven decisions worth understanding

These are the choices that will look arbitrary until you know the reason, and that you might otherwise "simplify" into a bug.

① The letterbox geometry lives in one shared header

preprocess_math.cuh is included by both the CUDA kernel and the CPU postprocessor. The kernel samples along a coordinate mapping; the postprocessor has to invert it to put boxes back on the camera frame. If those two disagree by half a pixel, every detection lands slightly off-centre, the turn command carries a constant bias, and the robot steers to one side of the target forever — while looking like it is merely badly tuned. So the mapping is defined once and both sides call it. The roundtrip is unit-tested: src → dst → src must be the identity.

② The kernel is fused, and there are two of them

Resize, BGR→RGB, /255, and HWC→CHW happen in one pass. Each is memory-bound alone, so four passes would move the frame through GPU memory four times to do a handful of arithmetic operations.

There are two kernels because the shared-memory optimisation has a limit. A 32×8 output tile needs a source window of roughly (32/scale) × (8/scale) pixels; as the camera resolution rises relative to the model input, that window grows until it will not fit in a block's shared memory. Rather than shrink the tile — which would break the coalesced 128-byte stores that make the fast path fast — the launcher falls back to a kernel that reads taps straight from global memory. Same arithmetic, same output, verified identical by verify_preprocess.

measured shared-memory requirement per block (32×8 tile)

  640×480  → 640×640    window 34×10     1,360 B     shared path
  800×600  → 640×640    window 42×12     2,016 B     shared path
 1024×768  → 640×640    window 54×15     3,240 B     shared path
 1600×1200 → 640×640    window 82×22     7,216 B     shared path
                                      ↑ limit is 48 KB; fallback is rarely hit

③ The block is 32×8, not 16×16

Both are 256 threads. 32 wide means one warp's 32 lanes write 32 consecutive floats — exactly 128 bytes, one full cache-line transaction — into the NCHW output. A 16-wide tile would split every warp's store across two output rows and two 64-byte segments, for no gain anywhere else. 256 threads is also the number that lets 6 blocks saturate an sm_86 SM's 1,536-thread limit.

④ The command link owns a thread and a one-slot mailbox

The naive version calls an HTTP GET inline, once per frame. When WiFi hiccups, that call stalls the entire vision loop, frames pile up, and the commands that eventually arrive describe where the target used to be.

Instead, post_command() drops the newest command into a single-slot mailbox and returns immediately. A worker thread sends it. If the network is slower than the vision loop, intermediate commands are overwritten and never sent — which is correct, because a stale steering command has negative value. Overwrites are counted and displayed, so the behaviour is visible rather than silent.

⑤ The firmware's logic contains no Arduino

balance_core.h has no #include <Arduino.h>, no String, no Serial, no delay(), and no dynamic allocation. Everything hard about the firmware — sensor fusion, PID anti-windup, the line parser, the arm/disarm state machine — is in there, and all of it is tested on a laptop at thousands of simulated timesteps per second. balance_controller.ino is the thin shell that reads the IMU and writes the motors.

This is not an abstraction for its own sake. On real hardware a bug in the parser, a bug in the PID, and a loose wire all present identically: the robot falls over and the only output is a serial cable.

⑥ The GPU pipeline runs on the default stream, deliberately

The stages are strictly dependent — preprocess needs the upload, inference needs preprocess — so there is nothing to overlap. More importantly, StageProfiler records its CUDA events without naming a stream. If the work were enqueued on a non-default stream, those events would not bracket the work they claim to measure, and the latency table would be quietly wrong. One stream keeps the measurement honest.

⑦ The ESP32 runs two HTTP servers

An MJPEG handler never returns; it loops pushing frames until the client disconnects. esp_http_server serves one request at a time per instance. Sharing a port would therefore queue /cmd behind the stream forever — the robot would receive video and no commands at all. Control is on port 80, the stream on port 81.

1.4  Where the subtle code is

Six places where the obvious version is wrong. Each is commented in place; they are collected here so you know they exist before you edit near them.

LocationThe trap
balance_controller.ino
wire_read16()		 The obvious (Wire.read() << 8) | Wire.read() is undefined-order in C++ — the compiler may read the low byte first, producing byte-swapped IMU samples. Two separate statements are sequenced; one expression is not.
balance_controller.ino
the PID call site		 The PID output is negated. The textbook error is setpoint − measurement, which is negative for a forward lean, but a forward lean must be caught by driving the wheels forward. The closed-loop simulation in the test suite exists to pin this down; with the sign flipped it diverges.
balance_core.h
Pid::update()		 D acts on the measurement, not the error, so a setpoint step — which is exactly what an incoming vision command is — produces no derivative spike. And the integral only accumulates when that would not push an already-saturated output further into saturation.
balance_controller.ino
the 200 Hz tick		 Timing uses unsigned subtraction (now − last < period), which stays correct across the ~71-minute micros() rollover. Comparing now > deadline does not. On overrun it resyncs rather than firing a burst of catch-up ticks with tiny dt.
preprocess.cu
the early return		 Threads outside the output region must still help load the shared tile, so the bounds check comes after __syncthreads(). Moving it earlier deadlocks the block.
main.cpp
FrameGrabber		 cv::VideoCapture buffers frames internally. Reading on the pipeline's thread means that whenever the pipeline is briefly slow, latency grows without bound and no amount of GPU optimisation helps — the delay is in a queue, not in compute. The grabber keeps exactly one frame: the newest.

Part 2Bringing it up in the real world

Non-negotiable rules
  1. Never tune with the wheels on the ground and your hands away. Hold the robot, or prop it so the wheels just clear the surface. A badly tuned balance loop drives at full PWM into whatever is nearest.
  2. Confirm the angle sign before arming the motors once. With the sign inverted the robot drives itself over, smoothly and confidently, and it looks exactly like a tuning problem. Stage 1 exists only for this.
  3. Charge LiPo cells on a balance charger, never unattended, never in the robot. This is a fire risk, not a performance note.
  4. Power the ESP32-CAM from the UBEC, not from the Mega's 5 V pin. The camera's inrush browns out the Mega's regulator and presents as Camera init failed 0x105 — a power fault that reads like a software fault.
  5. The level shifter on Mega TX → ESP32 RX is mandatory. 5 V into a 3.3 V pin damages the ESP32 — sometimes immediately, sometimes next week, which is worse.
  6. Keep a hand on the battery connector during first full runs. It is the fastest reliable off switch you have.

2.1  Seven stages, each with a gate

Do not proceed past a gate that has not passed. Every stage is testable without the stages after it — that is why the helper sketches and the --no-send flag exist.

Stage 0Tests, on a laptop, with no hardware at all
make -C test

Four suites: letterbox geometry, detector decoding, command shaping, and the entire balance-loop logic including a closed-loop pendulum simulation. No GPU, no TensorRT, no OpenCV, no network. Takes about a second.

Gate: all four suites report passing. If the pendulum simulation fails, the control logic or its sign convention is broken — fix that before touching hardware.
Stage 1IMU calibration and the angle sign check

Flash mcu/imu_calibrate.ino. Open the Serial Monitor at 115200. Follow its prompts: hold still for the bias measurement, then tilt the robot forward and watch the printed angle.

  • Angle goes positive when leaning forward → IMU_ANGLE_SIGN = +1.0f
  • Angle goes negative → IMU_ANGLE_SIGN = -1.0f
  • Rock it forward quickly: rate must have the same sign as the angle's direction of travel, otherwise flip IMU_RATE_SIGN

Also note the angle when the robot is balanced upright by hand — that is ANGLE_TRIM_DEG. And check which accelerometer axis reads ±1.0 at rest; the code assumes Z is vertical and X points along the direction of travel.

Gate: you can state both signs with confidence, and the angle tracks your hand smoothly without jumping.
Stage 2Motors, wheels off the ground

Flash balance_controller.ino with the signs from Stage 1. Prop the robot so the wheels spin freely. Power on — the motors will not move, by design: SafetyMonitor starts disarmed and requires the robot to be held within 4° of upright for 0.75 s before it arms. Watch arm% climb on the USB debug line.

Once armed, tilt gently forward. The wheels must spin forward. If one wheel is backwards, flip that wheel's LEFT_INVERT / RIGHT_INVERT. If both are backwards, your angle sign is wrong — go back to Stage 1. Never fix a direction problem by inverting the PID output; that also inverts the balance response.

Gate: arming works, both wheels respond in the correcting direction, and ovr= is not climbing (that would mean the 5 ms loop is missing its deadline).
Stage 3Tune the balance loop

Still propped, hands ready. One gain at a time. Full procedure is in §3.1 and at the bottom of balance_controller.ino.

Gate: the robot holds itself upright unassisted for 10+ seconds and recovers from a gentle push. No vision hardware is connected yet.
Stage 4ESP32-CAM alone, nothing attached

Set WiFi credentials and the static IP, flash, read the IP off the serial monitor. Then from the laptop:

curl "http://<ip>/status"                      # uptime, RSSI, counters
curl "http://<ip>/cmd?lean=0.00&turn=0.00"     # expect: OK

Open http://<ip>/ in a browser — you should see live video. Check RSSI on /status: weaker than about −70 dBm will stutter.

Gate: video in a browser, /cmd returns OK, RSSI acceptable from wherever the robot will actually be driven.
Stage 5The UART hop, with the motors unable to move

Wire the UART including the divider. Flash mcu/uart_echo_test.ino to the Mega — it never touches the motors, so the robot can lie on its side. Open the Serial Monitor, then from the laptop:

curl "http://<ip>/cmd?lean=1.50&turn=-0.25"   # line appears, marked -> OK
curl "http://<ip>/telemetry"                  # sweeping angle, AGE under ~100

Nothing arriving → wrong pins, no common ground, or the divider is backwards. Garbage characters → baud mismatch.

Gate: commands arrive and parse, telemetry flows back and is fresh. Both directions proven before the balance firmware returns.
Stage 6The vision pipeline, transmitting nothing
./build/verify_preprocess --bench          # kernel vs OpenCV, and timings
./build/reflex_cv --stream http://<ip>:81/stream \
                  --engine models/model.engine --no-send

--no-send shapes, displays and counts commands but never transmits them. Walk in front of the camera: the box should track you, the turn bar should lean the way you moved, and the values should move smoothly. This is where you tune the tracking gains (§3.2), with zero risk.

Gate: verify_preprocess reports PASS; detections are stable; commands look sensible and smooth; frame rate and dropped count are acceptable.
Stage 7Everything at once

Balance firmware on the Mega, bridge on the ESP32, pipeline on the laptop, --no-send removed. Floor, space, hand near the battery.

Expect to spend real time here. The thing that will need adjusting is how aggressive the vision commands are, against a real PID loop and real WiFi latency rather than against printed numbers. Adjust ShaperConfig on the laptop. Do not retune the balance PID — if it needs retuning once vision is attached, the commands are too aggressive, which is a laptop-side problem.

Gate: it tracks and follows without falling, and recovers sensibly when the target leaves the frame.

Part 3Tuning, measuring, and what breaks

3.1  Tuning the balance loop

Wheels just clear of the ground, hands ready, one gain at a time. Starting values are already in the file and are the ones the closed-loop simulation stabilises with for a 12 cm centre of mass — a real starting point, not a guess, but every chassis differs.

StepChangeWhat to look for
1KI = 0, KD = 0, raise KPRaise until the robot oscillates steadily — not until it balances. Then back off about 30%.
2raise KDUntil the oscillation damps and it feels stiff against a push. Too much makes it buzz at the gearbox's resonance — if it sounds angry, back off.
3add KI, smallUntil the slow one-directional drift stops. Too much gives a slow wallowing oscillation over a second or two — much slower than the KP oscillation, which is how you tell them apart.
4ANGLE_TRIM_DEGKills any remaining consistent creep. If it drifts forward, nudge positive.
5MOTOR_DEADZONERamp one wheel off the ground and note the PWM where it turns reliably. Too high → jittery; too low → small corrections do nothing.
If it drifts across the room but never falls

That is not a tuning failure. Angle-only balancing cannot distinguish "standing still" from "rolling at constant speed" — both are perfectly upright. The fix is wheel-velocity feedback: set ENABLE_ENCODER_DAMPING 1 and tune VEL_KD upward until it holds position. Do this only after the angle loop is tuned.

3.2  Tuning the tracking behaviour

All on the laptop, in ShaperConfig (src/command_shaper.h). Tune these with --no-send before ever tuning them against a moving robot.

3.3  Filling in the latency table

reflex_cv prints both timing tables on exit, plus markdown rows ready to paste into the README.

./build/reflex_cv --stream http://<ip>:81/stream --engine models/model.engine \
                  --no-send --headless --max-frames 1000 --csv run1.csv

Read p95, not max. Max is usually one startup outlier; p95 is what the robot actually lives with frame after frame.

To measureHow
Shared memory, before/afterverify_preprocess --bench times both kernel variants back to back. That is the honest before/after for the optimisation claim.
FP16, before/afterBuild a second engine without --fp16, run both with --max-frames, compare the inference row.
Batching's real cost--batch 1 vs --batch 4. Throughput rises, end-to-end latency rises too — for a single camera driving a balance loop, latency is what matters.
The network's contributionCompare the capture-wait row across resolutions using /res?size=. Restart the pipeline after changing it.
Cost of profiling itself--no-profile. Each stage's stop() synchronises, so measurement is not free.

3.5  Demo day

  • Decide your fallback before you run out of time. A robot that balances perfectly and does one simple robust thing beats a fragile impressive one. The simplest credible fallback: follow a brightly coloured ball with --class 32, which is far easier than tracking people in a crowded room.
  • Test the room's WiFi in advance, and bring a phone hotspot as a tested backup. A demo room full of laptops is the worst 2.4 GHz environment you will meet.
  • Re-run imu_calibrate at the venue. Gyro bias drifts with temperature, and the firmware re-measures at boot — but confirm the robot really was still during that three-second window.
  • Have the latency table filled in. The measured before/after numbers are the most interesting thing about the project to anyone technical, and they take one headless run to produce.
  • Charge batteries the night before, on a balance charger, attended.

What to expect on first contact with hardware
  • The ESP32 sketch will probably need small fixes on its first build. It is the one file with no compiler verification. Budget an hour; expect an include or an enum name, not a design problem.
  • The TensorRT wrapper may need signature corrections against your actual SDK version. The error messages will be compiler errors at the call sites, which are few and clearly marked. The #error at the top of trt_infer.h catches a too-old SDK immediately.
  • The CUDA kernel has never run. Its arithmetic is heavily unit-tested on the host and it compiles for both target architectures, but the first thing to do after building is verify_preprocess, which exists precisely to check it against OpenCV on a real GPU.
  • The PID gains are simulation-derived, for a 12 cm centre of mass. They are a real starting point, not a guess — but your chassis is not the simulation, and you will retune.
